Tổng quanOverview

Gateway làm gì cho bạnWhat the gateway does for you

Gateway kết nối hệ thống cuộc gọi với AI agent của bạn. Gateway giữ phần kết nối thoại ở phía mình và phơi ra ba bề mặt công khai: REST endpoint để đổi token, REST GET để đọc lịch sử bền vững, và WebSocket realtime để nhận sự kiện, truyền audio hai chiều, và gửi lệnh điều khiển cuộc gọi. Gateway connects the call service to your AI agent. It keeps call connectivity on its side of the boundary and exposes three public surfaces: a REST endpoint that exchanges your key for a token, REST GET endpoints for durable history, and a realtime WebSocket for events, bidirectional audio, and scoped call-control commands.

Xác thựcAuthentication

API key và token realtimeAPI keys and realtime tokens

API key là bí mật dài hạn, dùng trong header Authorization: Bearer để đổi token realtime hoặc đọc lịch sử bền vững. Không bao giờ đặt API key lên query string, không log, không commit vào repo. The API key is a long-lived secret sent in the Authorization: Bearer header for realtime token exchange or durable history reads. Never put the key in a query string, a log line, or a repository.

Quy tắc vận hànhOperating rules

  • Token là dùng một lần cho mỗi kết nối. Mỗi lần kết nối lại phải xin token mới; không phát lại token cũ.One token per connection. Mint a fresh token on every reconnect; never replay an expired one.
  • Retry xác thực có giới hạn. Luồng kết nối của SDK (Python run()/stream(), Node start()) tự thử lại lỗi xác thực 3 lần sau lần đầu (tổng 4 lần). Một ngân sách chung áp dụng cho HTTP 401/403 khi đổi token, HTTP 401/403 ở WebSocket handshake và close 4401; mỗi lần thử lại xin token mới, chờ 1, 2, rồi 4 giây nếu chỉ gặp lỗi xác thực, tối đa theo max_backoff/maxBackoffMs. Ngân sách chỉ reset khi nhận session.ready.Bounded authentication retry. SDK connection flows (Python run()/stream(), Node start()) retry authentication failures 3 times after the initial attempt (4 attempts total). One shared budget covers HTTP 401/403 from token exchange, HTTP 401/403 from the WebSocket handshake, and close 4401; each retry mints a fresh token, waiting 1, 2, then 4 seconds for authentication-only failures, capped by max_backoff/maxBackoffMs. The budget resets only when session.ready arrives.
  • Dừng đúng cách. Đặt reconnect=False hoặc reconnect: false để tắt retry tự động; close() sẽ dừng retry đang chờ, còn huỷ task Python cũng dừng chúng. Hết ngân sách, Python raise AuthenticationError; Node start() ban đầu sẽ reject, còn lần reconnect về sau sẽ phát lỗi trên error rồi dừng client. Key đã thu hồi không thể sống lại nhờ retry. Các helper realtime_token()/realtimeToken() chỉ gửi một request, không tự retry lồng nhau.Stop deliberately. Set reconnect=False or reconnect: false to disable automatic retries; close() stops pending retries, and Python task cancellation also stops them. Once the budget is exhausted, Python raises AuthenticationError; Node's initial start() rejects, while a later reconnect emits it on error and stops the client. A revoked key cannot be revived by retrying. The realtime_token()/realtimeToken() helpers make one request and do not retry themselves.
  • Giới hạn tần suất. Mặc định 60 lần đổi token mỗi phút cho mỗi key. Vượt ngưỡng trả 429.Rate limit. 60 token exchanges per minute per key by default. Exceeding it returns 429.
  • Thu hồi có hiệu lực tức thì. Khi key bị thu hồi hoặc hết hạn, gateway chặn cả việc cấp token mới lẫn kết nối WebSocket mới.Revocation is immediate. A revoked or expired key blocks both token minting and new WebSocket sessions.
  • Xoay vòng key không có thời gian ân hạn. Lệnh rotate cấp key mới và thu hồi key cũ ngay lập tức.Rotation has no grace period. Rotating issues the replacement and revokes the old key at the same moment.

Kết nối realtimeRealtime session

Mở phiên và giữ phiên sốngOpening and holding the session

WebSocketwss://<gateway>/v1/realtime?token=…
// 1 — partner → gateway, ngay sau khi mở / immediately after open
{"type":"session.register","agent_slug":"support-agent","protocol_version":"1"}

// 2 — gateway → partner
{"type":"session.ready","connection_id":"1f0c…"}

// 3 — partner → gateway, mỗi 10 giây / every 10 seconds
{"type":"heartbeat"}

// 4 — gateway → partner
{"type":"heartbeat.ack"}

agent_slug bạn gửi phải trùng đúng slug gắn với API key, và protocol_version phải là chuỗi "1". Sai một trong hai, gateway trả lỗi registration-rejected. The agent_slug you send must match the slug bound to your API key, and protocol_version must be the string "1". Either mismatch returns registration-rejected.

Mỗi slug chỉ có một kết nối sống, và kết nối đăng ký sau cùng được giữ. Khi một client mới đăng ký slug đang có người giữ, kết nối cũ nhận lỗi session-superseded, mọi cuộc gọi của nó bị cúp, rồi nó bị đóng với mã 4409. Kết nối cũ không được tự kết nối lại, nếu không hai client sẽ giành slug của nhau mãi. Hãy chạy một client duy nhất cho mỗi slug, hoặc dùng slug riêng cho từng instance. Each slug has one live connection, and the most recent registration keeps it. When a new client registers a slug that is already held, the old connection gets session-superseded, every call it owns is hung up, and it is closed with 4409. The old connection must not reconnect, or two clients will take the slug from each other forever. Run a single client per slug, or give each instance its own slug.

call.status trả dialing (đang gọi), ringing (đổ chuông), answered (đã nhấc máy). Chờ call.started để bắt đầu audio. Khi kết thúc, nhận call.status với terminal: true, rồi call.ended kèm kết quả và mã nguyên nhân.call.status reports dialing, ringing and answered. Wait for call.started before audio. Termination produces call.status with terminal: true, followed by call.ended carrying the result and cause.

Kết quả cuối: completed (đã nghe rồi dập máy), busy (bận), no_answer (không trả lời), rejected (bị từ chối), unavailable (không liên lạc được), failed (lỗi), cancelled (hủy trước khi nghe). Gateway phân loại dựa trên tín hiệu cuộc gọi và thời hạn quay số; cùng một mã nguyên nhân có thể bao quát nhiều hành động trên điện thoại.Final results: completed, busy, no_answer, rejected, unavailable, failed, cancelled. Gateway classifies them from call signals and the dialing deadline; one cause can cover more than one handset action.

Mỗi lần đọc call.status qua WebSocket chỉ là một snapshot trong phiên. Dùng bề mặt GET ở mục lịch sử bền vững để đọc danh sách và timeline sau khi reconnect hoặc khởi động lại.Each WebSocket call.status read is a snapshot within the session. Use the durable history GET surface for lists and timelines that survive reconnects or restarts.

Để kiểm tra theo call_id, key cần calls:read. SDK hiện có dùng được ngay:Check by call_id with calls:read. Existing SDKs work immediately:

await client.control(call_id, "call.status")  # Python
client.control(callId, "call.status");       // Node.js

Phản hồi là call.status với request_id tương ứng, không phải call.control.accepted. Truy vấn luôn đọc trạng thái mới nhất. Chỉ xem được cuộc gọi của chính kết nối WebSocket; giữ tối đa 256 kết quả đã kết thúc trong phiên. Mất kết nối, khởi động lại hoặc bị loại khỏi bộ nhớ thì không tra lại được; dùng GET ở mục dưới nếu cần lịch sử lâu dài.The reply is call.status with the matching request_id, rather than call.control.accepted. Every query reads fresh state. Only the owning WebSocket can read its calls; up to 256 completed results remain in that session. Disconnect, restart or eviction clears access; use the GET surface below for durable history.

Lịch sửHistory

Lịch sử bền vững qua REST GETDurable history through REST GET

Lịch sử bền vững là bề mặt đọc HTTPS riêng. Gửi API key trực tiếp trong header Authorization: Bearer; không đổi sang realtime token và không cần mở WebSocket. Key phải có scope calls:read. Mỗi request bị giới hạn đồng thời theo organization và partner app của key. Durable history is a separate HTTPS read surface. Send the API key directly in the Authorization: Bearer header; do not exchange a realtime token and do not open a WebSocket. The key needs the calls:read scope. Every request is restricted to both the key's organization and partner app.

AudioAudio

Khung nhị phân: 16 byte UUID rồi tới PCMThe binary frame: 16 UUID bytes, then PCM

Audio đi theo cả hai chiều trên cùng WebSocket, dưới dạng khung nhị phân. Mỗi khung bắt đầu bằng 16 byte thô của call_id (UUID RFC 4122, dạng nhị phân — không phải chuỗi 36 ký tự), phần còn lại là audio thuần. Audio travels both directions on the same WebSocket as binary frames. Each frame opens with the 16 raw bytes of the call_id (an RFC 4122 UUID in binary form — not its 36-character string), and everything after that is raw audio.

Cùng một định dạng cho cả chiều gateway → partner và partner → gateway. SDK chính thức tự đóng và gỡ lớp bọc này; nếu tự dựng khung, ngoài 16 byte UUID đừng chèn thêm byte nào khác. The same layout in both directions. The official SDKs add and strip this envelope for you; if you frame by hand, never prepend anything beyond the 16 UUID bytes.

Tần số lấy mẫu do gateway công bố, không cố địnhThe sample rate is announced, not fixed

Mã hoá luôn là PCM signed 16-bit little-endian, mono. Nhưng tần số thì không cố định: mỗi cuộc gọi, gateway công bố tần số thật trong khối media của call.started. Hãy đọc con số đó và dùng nó — đừng gán cứng. The encoding is always PCM signed 16-bit little-endian, mono. The rate is not fixed: the gateway announces the real one per call in call.started's media block. Read that number and use it — do not hardcode.

Mặc định là 8000 Hz. Một cấu hình Gateway nối các thiết bị đầu cuối băng rộng thật sự có thể công bố tần số cao hơn, và khi đó cùng một đoạn mã của bạn phải hoạt động được mà không cần sửa. The default is 8000 Hz. A Gateway configuration that connects genuinely wideband endpoints may announce a higher rate, and the same code of yours has to keep working when it does.

Vì sao điều này quan trọng hơn vẻ ngoài của nóWhy this matters more than it looks

Mỗi lần đổi tần số là một lần lấy mẫu lại, và không phải lần nào cũng vô hại. Bộ lọc chống chồng phổ trong hầu hết các thư viện chỉ xử lý được tỉ lệ nguyên. Nếu mô hình của bạn phát ra 24 kHz và bạn ép nó về 16 kHz, tỉ lệ là 1,5× — nhiều thư viện sẽ âm thầm bỏ bộ lọc và nội suy tuyến tính, để lại méo tiếng mà log không hề báo. 24 kHz về 8 kHz là 3×, tỉ lệ nguyên, và giữ nguyên bộ lọc. Every rate change is a resample, and not all of them are harmless. The anti-alias filter in most libraries only handles integer ratios. If your model emits 24 kHz and you force it to 16 kHz, the ratio is 1.5× — many libraries silently drop the filter and interpolate linearly, leaving aliasing that no log reports. 24 kHz to 8 kHz is 3×, an integer ratio, and keeps the filter.

Trên đường gọi thực tế, đường 16 kHz đặt 56% năng lượng giọng nói trong dải thoại 300–3400 Hz, còn đường 8 kHz đạt 68%. Người nghe mô tả sự khác biệt là “ồm ồm, xa xăm”. Tần số cao hơn không tự làm cuộc gọi rõ hơn — nó chỉ thêm những bước đổi tần số mà bạn phải xử lý. On a live call path, the 16 kHz wire put 56% of speech energy in the 300–3400 Hz telephony band, while the 8 kHz path reached 68%. Listeners described the difference as “boomy and far away”. A higher rate does not automatically make the call clearer; it only adds resampling steps for you to handle.

Nếu bạn tự dựng khung thay vì dùng SDK: hãy giữ tần số công bố cho từng call_id và dùng nó cho cả hai chiều. Audio đến từ gateway cũng ở đúng tần số đó. If you frame by hand instead of using an SDK: keep the announced rate per call_id and use it in both directions. Audio arriving from the gateway is at that same rate.

Chống trùng lặp bằng request_idIdempotency with request_id

Đặt một UUID vào request_id cho mọi lệnh bạn có thể phải gửi lại. Kết nối hiện tại ghi nhớ kết quả đã chấp nhận và trả lại đúng phản hồi cũ thay vì chạy lại thao tác điều khiển lần thứ hai. Bộ nhớ này giữ 256 request gần nhất và mất khi kết nối đóng. Put a UUID in request_id on every command you might retry. The current connection remembers accepted results and replays the original response instead of running the control action twice. That memory holds the last 256 requests and is lost when the connection closes.

Allowlist đíchDestination allowlist

Mọi lệnh transfer.* (trừ transfer.cancel), route.* và outbound.originate đều phải có context và extension ghép thành chuỗi context:extension được allowlist của partner app chấp nhận. Every transfer.* (except transfer.cancel), route.*, and outbound.originate must carry a context and extension whose context:extension pair is accepted by your partner app's allowlist.

Entry thường là cặp context:extension chính xác. Extension kết thúc bằng * là luật tiền tố: from-internal:84* cho phép mọi extension dài hơn bắt đầu bằng 84 trong context đó — đây là cách gọi ra hoạt động khi số đích đổi theo từng cuộc gọi. Luật cố tình hẹp: Entries are usually exact context:extension pairs. An extension ending in * is a prefix rule instead: from-internal:84* permits any longer extension starting 84 in that context, which is how outbound dialing works when the callee differs on every call. The rules are deliberately narrow:

  • Chỉ dấu sao ở cuối mới là ký tự đại diện, nên feature code như *43 vẫn là đích chính xác.Only a trailing * is a wildcard, so feature codes like *43 stay exact destinations.
  • Tiền tố cần tối thiểu hai ký tự thật — một ký tự không phải là ràng buộc.A prefix needs at least two literal characters — one is not a restriction.
  • Luật không bao giờ khớp đúng phần tiền tố (84* không cho quay 84) và không bao giờ lan sang context khác.A rule never matches the bare prefix itself (84* does not permit dialling 84) and never crosses into another context.
  • context — 1–80 ký tự thuộc A–Z a–z 0–9 _ -context — 1–80 characters from A–Z a–z 0–9 _ -
  • extension — 1–80 ký tự thuộc A–Z a–z 0–9 * # + _ -extension — 1–80 characters from A–Z a–z 0–9 * # + _ -

Sai cú pháp hoặc không có trong allowlist đều trả command-denied. Đây là lỗi cấu hình, không phải lỗi tạm thời — thử lại không giúp ích. Bad syntax and a missing allowlist entry both return command-denied. That is a configuration error, not a transient one — retrying will not help.
